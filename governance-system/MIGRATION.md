# Governance Suite v1 to v2

## Active skill migration

The only skill source is one Git-tracked tree holding the three packages as siblings
(`<skills-root>`):

- `<skills-root>/governance-system`
- `<skills-root>/plan-waves-slices`
- `<skills-root>/spec-chain`

Install by pointing the Cursor and Claude Code skill directories
(`~/.cursor/skills/<skill>`, `~/.claude/skills/<skill>`) at those packages, either
directly or through a stable runtime path such as `~/.local/share/agent-skills`;
`scripts/validate_suite.py --check-symlinks` verifies the resulting layout. Whatever
repository hosts the tree documents its own install and projection commands. The three
packages must stay siblings: `governancectl validate` locates the spec-chain and plan
validators relative to its own resolved path. The previous v1 skill copies and rollback
utility have been removed.

## Runtime state v2 to v3

Config schema 3 removes machine-specific fields from the committed
`.governance/config.json`:

- `repository_id` is now derived from the repository's root commit(s), so the same
  committed file is valid in every clone and worktree. v2 derived it from the absolute
  Git common directory path, which broke on clone.
- `canonical_worktree` and `canonical_branch` moved to machine-local
  `<git-common-dir>/governance/canonical.json`; `governancectl set-canonical --path`
  changes them.

`load_config` migrates a v2 file in place on first contact when its recorded canonical
worktree still exists on this machine; otherwise the main worktree becomes canonical
until the owner runs `set-canonical`. Commit the rewritten config.

## Repository compatibility

Repositories generated by v1 remain readable. V2 changes authority and workflow:

- `AGENTS.md` becomes the platform-neutral hub; `CLAUDE.md` is a thin adapter.
- `.cursor/rules/governance.mdc` is the Cursor adapter.
- `docs/waves/README.md` is the only wave-status authority.
- code-derived facts move from binding decisions to non-binding Observations.
- FSD, TSD and design baselines are written before wave decomposition.
- `spec-chain` owns canonical FSD/TSD authoring; Word/client editions are derived.
- slices are PR-sized review units rather than mandatory single commits.
- worktree state and R-ID resolutions gate stage closure.
- hooks are opt-in per project.

## Updating an existing governed repository

1. Run governance audit and worktree reconciliation first.
2. Snapshot existing governance documents.
3. Add `.governance/config.json` through `governancectl discover`.
4. Set `project_slug` in that config to the basename used by
   `docs/<project>-FSD.md` and `docs/<project>-TSD.md`.
5. Migrate authority one concern at a time; do not replace project-specific prose.
6. Move mutable status to the waves index and replace copied tables with links.
7. Move unratified code facts to Observations or Open items.
8. Reconcile existing specifications:
   - preserve their project-specific content;
   - assign stable F-IDs to behavioral requirements;
   - move implementation material from FSD to TSD;
   - assign T-IDs and map every F-ID;
   - rename risk IDs to RK-IDs and open decisions to canonical O-IDs;
   - remove milestones or work breakdown from TSD.
9. Update wave briefs to cite F-IDs and T-IDs without redefining them.
10. Add `AGENTS.md` and thin platform adapters.
11. Validate specifications, waves and governance before installing hooks.

The skill performs these steps as update mode. It must present content conflicts to the
owner rather than selecting a document version automatically.
